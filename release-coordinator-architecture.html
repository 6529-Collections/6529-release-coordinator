Ask for a release

What happens

The developer tells the existing agent what should go to staging or production. There is no new form or manual JSON work. 


          


          

            Implemented boundary
            

              Today, the CLI creates and validates the request. Every run is saved locally. Only a
              valid request is added to the local outbox.
            

            

              Frontend and backend release instructions use the CLI submit command as a
              synchronous observation step. A combined release records one shared request.
            

            

              The public CLI starts one workflow, waits for it, and returns success or failure
              with the inbox Issue result. A normal returned result does not stop the existing
              authorized release flow.
            

            

              The central workflow now saves each accepted request as one public GitHub Issue.
              The inbox needs no new server or database. Requests and workflow logs are public
              and must never contain secrets.
            

            

              The local inbox reader checks open requests against their workflow results.
              A separate readiness command checks current PR evidence and backend dependency
              order. Both print reports without changing GitHub. Missing release history and
              execution merge proof remain unknown. No release worker exists yet.
            

            

              One ticket workflow: Run inbox:run with a
              profile and ticket. It checks the saved request and handles initial blockers,
              creates the merge plan from the ticket and configured destinations,
              tries suitable PRs locally, runs supported sandbox service/database checks,
              and updates that same ticket with reasons and separate Git and service results.
              The original receipt stays intact.
              See the ticket contract and
              local versus live evidence.
            

            

              Passing is still pre-release: The ticket shows
              rehearsal:passed for Git and services:passed for
              successful sandbox application checks, and waits for future execution. Sandbox and
              real profiles share the same code. No product merge, build, or deployment
              runs. See the profile guide.
            

            

              Implemented and tested in sandbox: One ticket's database,
              worker, API, and frontend checks run in dependency order. Temporary MySQL
              and fake data run in the test backend's GitHub Actions job and are cleaned
              up afterward. Database answers, failures, and retries have recorded evidence;
              see the service/database guide.
              Source delivery
              records the Coordinator PR and CI separately from these sample tests. The next
              development stage is testing batches
              without database changes, keeping excluded tickets visible with reasons.
              Batching remains unimplemented.
            

            

              Source: packages/release-request/. Product repositories install only
              @6529-collections/release-request. The private Coordinator lives separately
              in apps/coordinator/ and is not installed by product repositories.
