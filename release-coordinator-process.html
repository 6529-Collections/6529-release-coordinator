Release steps

    Implemented today: Frontend and backend record new release intents through the public CLI and central GitHub Issue workflow. The local reader verifies open request records and the readiness command inspects current PR and dependency evidence. Both print reports without changing tickets or authorizing a release. The release worker, durable release queue, product merges, release builds, deployments, and recovery described below remain proposed work. See progress and evidence and the implemented intake path.

    Inbox organization, before this release flow: Organize the inbox with readable tickets, status/reason labels, submitter ownership, and recorded decisions. The single inbox:run command checks tickets, rehearses suitable exact PRs, runs supported sandbox service checks, and records the results on the same ticket. Inspection commands remain read-only. See the ticket contract and progress for rollout evidence.

    Implemented and tested in sandbox: One ticket's database change, worker, API, and frontend checks run in dependency order. The test backend's GitHub Actions job creates temporary MySQL with fake data and removes it after saving the result. Successes, failures, held requests, and retries have local and live evidence. Coordinator PR/CI delivery is recorded separately in progress. This is not a real deployment. See the service/database guide and evidence.

    Sandbox batching: Complete cheap checks for every ticket and filter Git conflicts, then test a selected group without database changes. Divide confirmed failures within limits while keeping tickets and required dependencies whole. Excluded tickets keep a reason and next action; a failed combination does not make every request broken. See the batch rules and ticket outcomes. The local implementation uses temporary PR checks followed by combined service tests. Progress separates local checks from live acceptance and source delivery.

    Agreed September 11; execution is not built: One release at a time. Reuse existing product Actions and their separate staging/production builds. Wait for successful matching staging E2E before merging into main for production. Rollback uses new revert commits and ordinary deployments only when no database change is confirmed and restoration is safe; otherwise a person takes over. See the agreed rules. A staging request alone never authorizes production.

    Storage built locally; live migration pending: Use the existing GitHub journal: keep active work complete and archive finished records in the same repository. Read old details only when needed, preserving retries and cleanup evidence. Lifetime record caps are removed; each search still has fixed work limits. No separate database, heartbeat or dashboard is required. The current journal is not yet an executing release queue. See the history storage.
